## The problem with single-player AI in a lab

Science happens in teams, but AI assistants are built for one person at a time. Every session starts from a blank prompt, and whatever one person works out stays in their own history. In a lab that looks like two people on the same team asking related questions in separate chats, each rebuilding context the other already has, while a fix that helps one scientist never reaches the next. The team gets faster one person at a time and never together.

## What the system does

The system works across the team's sessions instead of inside one. When you ask it something, it can pull in context from a teammate's session when that context matters, so a result someone found last week shows up in your work without anyone having to forward it. Underneath the sessions sits a knowledge graph of the team's work, and that graph is how the system connects the dots between people, questions and findings that would otherwise live in separate chats.

Teammates can also open each other's sessions and build on them directly. Anyone using the system can change its code base, so whoever runs into a gap can close it, and the system learns from how the team uses it in a weekly self-improvement cycle.

## Finding the work worth hardening

Before deciding what to build, I watched how the scientists actually worked. I ran user studies and observation studies and mapped their workflows step by step. Some of that work is exploratory and different every time, which is where an agent helps most. Other parts run the same way on every project, and there an agent's flexibility is a liability, because a step that should be identical every time shouldn't depend on how a model reads the prompt that day. So I built deterministic workflows on top of the system to harden those steps, and left the agents to the exploratory work.

## Building it myself

I own the product features and the vision for where the system goes. Running rapid experiments with the teams using it, I also built and shipped **5+ collaboration features** myself, without engineering support, which meant an idea could reach scientists without waiting for a slot on anyone's roadmap.

## Knowing whether it works

A system that changes itself every week needs a way to catch itself getting worse. I defined how we measure it: session success rate for whether people got what they came for, LLM-as-judge evaluation for the quality of what the system produced, and regression tracking so a weekly improvement can't quietly break something that used to work.

Sharing by default only works if people trust what's being shared. As the system spread from one team to many, I managed its data privacy boundaries, deciding what moves across teams and what stays with the team that produced it.

## From one team to the org

It started as one team's project. Once it was working there, we rolled it out across the whole org, more than 1,000 people, and in its first month it reached **35% adoption**, with **300+ users** across 5+ teams running **more than 100,000 sessions**.

## What I'm working out

Single-player AI made each of us faster, and the question I'm working on now is what makes a team faster. Most of it comes down to defaults and trust: which work should be shared automatically, how a team trusts a change someone else made to a system everyone depends on, and how a system that learns from everyone keeps working for each person.
