## The problem

PointClickCare builds cloud software for senior care and post-acute providers, so the people using it are clinicians in the middle of a shift. A slow page or a form that behaves differently from the last one takes time away from a resident, which makes frontend quality part of the product. I was a software engineer on the provider portal, one of PointClickCare's web apps for healthcare providers, and two things decided how fast it could improve: how screens were built, and how long every change waited on CI.

## The calls I made

### One component library instead of many copies

I built the portal's UI component library, the shared components every screen is assembled from. Instead of each team rebuilding the same pieces slightly differently, the portal got one set of components that look and behave the same everywhere, and new screens start from parts that are already tested.

### Treat CI time as product time

Every engineer waits on CI before they know whether a change is safe to merge, so its run time is a tax on everything the team ships. I optimized the CI pipelines and cut their run time **30%**.

## What I learned

Shared components and fast CI solve the same problem from two ends. Both make the right way to build something the fastest way too, and teams follow the fast path. For software clinicians use mid-shift, that meant a consistent screen and a fix that reached them sooner.
